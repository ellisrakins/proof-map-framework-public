# Paper CI Alpha acceptance

The alpha contract is executable. The bounded implementation is packaged as
candidate `0.8.0a1`; readiness is determined by exact-source/package qualification,
not declared by this document or inferred from the version number.
The completed paper-to-evidence milestone in PRs #5 and #6 remains complete.
The active ledger records candidate implementation and required execution evidence
separately. The candidate's `alpha-acceptance.json` and required checks establish
its qualification state. Production authority, package-index publication and
scholarly acceptance remain separate from software readiness.

## Contract and evidence

[`acceptance/paper_ci_alpha.json`](../acceptance/paper_ci_alpha.json) is the active
ledger: inherited requirements, supported domains, implementation gaps, positive
and negative test selectors, execution profiles, jobs, artifacts, twelve fixture
categories and five installed-package scenarios. `already_implemented` is an
implementation assessment, never a passing readiness verdict. Every mandatory
row still needs current execution evidence.

[`acceptance/mandatory_requirements.json`](../acceptance/mandatory_requirements.json)
preserves the mandatory inventory and original section references. The checker
rejects deleted requirements or changed inherited scope. Scope changes require
explicit review and original authority; this increment authorizes none.
[`alpha_acceptance.schema.json`](../schema/alpha_acceptance.schema.json) and
[`alpha_evidence.schema.json`](../schema/alpha_evidence.schema.json) define the
manifest and evidence envelope contracts.

[`scripts/alpha_evidence.py`](../scripts/alpha_evidence.py) captures observed
pytest outcomes or one command execution. Each report records the tested commit,
Git tree, actual source fingerprint, PR head when applicable, run ID, run attempt,
package version and manifest digest, with its producing job and runner profile.
The source fingerprint includes tracked changes and nonignored untracked files;
a commit SHA alone cannot identify an uncommitted candidate. Source changes
during execution invalidate the report. Later source changes make earlier
reports stale for that candidate, including documentation or manifest edits.

[`scripts/check_alpha_acceptance.py`](../scripts/check_alpha_acceptance.py)
compares these identities with the current candidate, validates schemas and
artifact bytes, and resolves actual collected test identities. Missing, empty,
malformed, duplicate, mixed-revision or stale reports cannot establish readiness.
Required selectors must collect and pass: skipped, xfailed, xpassed, failed or
unexecuted mandatory tests fail their requirement. An unrelated optional skip
does not fail a passing mandatory selector. Empty positive/negative mappings and
implementation gaps remain explicit failures or unexecuted requirements.

Reports are execution records from the trusted software workflow, not signed
mathematical authority. The isolated-paper artifact must demonstrate the real
paper-to-evidence driver, fresh replay, fidelity decisions and rejection cases.
A generic Docker check, host Lean run or worker test double cannot replace that
artifact. Extraction benchmarks measure extraction, not verified proofs.
Missing role labels remain unknown only for fixtures whose source-bound golden
entry omits that dimension; they provide no positive accuracy or corpus-coverage
evidence. Dependency audits must cover third-party packages without findings or
skips. The project's exact-version unpublished-self skip remains explicit in
the retained audit artifact; publishing this package is not an alpha prerequisite.

## Local use

Use the development environment described in [CI.md](CI.md). Finish source edits
before collecting evidence, keep outputs in ignored `.work/`, and choose a fresh
run ID for each qualification. The following PowerShell example runs only the
gate's focused regressions; it cannot satisfy the full alpha contract:

```powershell
$env:ALPHA_RUN_ID = "local-" + [guid]::NewGuid().ToString("N")
$env:ALPHA_RUN_ATTEMPT = "1"
python -m pytest -p scripts.alpha_evidence `
  --alpha-evidence .work/alpha-local/gate/evidence.json `
  --alpha-job workflow-security --alpha-profile windows-unit `
  tests/test_alpha_acceptance.py tests/test_alpha_evidence.py tests/test_ci_required.py -q
python scripts/check_alpha_acceptance.py `
  --evidence-dir .work/alpha-local `
  --out .work/alpha-acceptance.json --summary .work/alpha-acceptance.md
```

Keep the same run ID and attempt while producing and checking one candidate's
reports. Give each producer its own envelope directory and report its actual
profile; labeling a Windows run as Linux does not provide Linux validation.
The command wrapper also supports `command --job JOB --profile PROFILE --out
PATH --artifact NAME=PATH -- COMMAND ...`; artifacts must be generated by that
execution and live below the envelope directory. Reuse toolchain/dependency
caches, never cached verdicts as fresh execution evidence.

The checker writes JSON and a readable summary, and exits `0` only for `READY`.
Exit `1` and `NOT_READY` are expected while mandatory implementation, evidence
or release-version requirements remain open. Per-row `PASS`, `FAIL` and
`UNEXECUTED` counts and reasons distinguish these cases. The active manifest,
not a dated test total or historical traceability table, defines the work left.

## CI and release boundary

The normal software workflow uploads evidence from its existing test and
execution jobs. `alpha-readiness` consumes those reports and artifacts from the
same checkout/run attempt, without rerunning the matrix, and emits
`alpha-acceptance.json` plus its readable summary. `ci-required` depends on
`alpha-readiness` as well as every previous mandatory job. This deliberately
makes `ci-required` non-success while the full alpha remains incomplete; a green
unit suite cannot bypass that decision. Historical hosted runs qualify only
their recorded source identities. Each newly published revision needs its own results.

Release metadata must change only when the capability gates justify it, followed
by qualification of the actual versioned source and distribution. Publishing,
production keys, OCR, paid integrations and scholarly acceptance are not alpha
readiness prerequisites. Extracted author claims, generated formal subjects,
formal verification, authenticated fidelity decisions and acceptance under a
named policy remain separate states; none establishes universal theorem proving
or scholarly acceptance.
